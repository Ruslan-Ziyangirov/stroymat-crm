# СТРОЙМАТ CRM

Внутренняя CRM-система компании «СТРОЙМАТ» (продажа строительных материалов):
клиенты и заказы, автоматическая помесячная отчётность, разбор внешних выгрузок,
оценка районов для открытия магазина, бонусная программа и обмен данными с 1С.

## Стек

## Что реализовано

**01. Базовая CRM**
- Клиенты (`/clients`) — простой список карточек: имя, телефон, ответственный менеджер, магазин,
  сводка по заказам. Справочник «кому продаём», без собственного статуса и воронки — конкретная
  сделка живёт на заказе, у одного клиента их может быть несколько за время работы с ним.
- Заказы, товары, магазины, три роли (`admin`, `director`, `manager`) с разграничением через RLS.

**01a. Воронка продаж по заказам** (`/orders`, канбан-доска — единственный вид списка заказов)
- Заказ = сделка, и полностью заменяет прежний статус доставки (новый/подтверждён/оплачен/в
  доставке/выполнен/отменён) этапами воронки: Новый лид → Первый контакт → КП отправлено → Встреча
  назначена → Продажа / Условный отказ → Закрыто и не реализовано. Порядок и подписи —
  `DEAL_STAGE_ORDER`/`DEAL_STAGE_LABELS` в `src/lib/constants.ts`.
- Перевод сделки на новый этап (drag-and-drop или кнопка «Следующий шаг») всегда идёт через диалог
  `NextStepDialog` → серверный экшен `moveOrderStage`: часть этапов требует обязательных полей
  (бюджет/приоритет/товар/тип сделки и сумма КП — для «КП отправлено»; дата и время — для «Встреча
  назначена»; причина и комментарий — для «Условный отказ»), а для всех нетерминальных этапов —
  обязательную следующую задачу (ответственный, точный дедлайн, тип действия, комментарий).
  Проверки — на сервере, не только в форме.
- «Закрыто и не реализовано» доступно только из «Условный отказ» и только руководителю/администратору
  — менеджер сам сделку «не реализованной» закрыть не может.
- Бонус клиенту (1 % от суммы) начисляется автоматически триггером БД в момент, когда заказ выходит
  на этап «Продажа» (раньше — при статусе «Завершён»).
- Лимит активных сделок на менеджера (по умолчанию 80, таблица `pipeline_settings`, редактируется
  инлайн над доской только руководством) — при попытке завести заказ сверх лимита сервер отказывает.
- На карточках — предупреждения «нет задачи» / «просрочено» / «долго на этапе», плюс быстрые фильтры
  над доской по этим же признакам; на дашборде эти же признаки собраны в блок «Сделки, требующие
  внимания».

**02. Загрузка и анализ отчётов** (`/uploads`)
- Приём `.xlsx` / `.csv`, автоматическое распознавание колонок (русские и английские заголовки).
- Оригинал файла сохраняется в Supabase Storage, строки — в таблицу `report_rows`.
- Объединение всех загрузок в общую отчётность, сравнение периодов.
- Поиск отклонений (> 30 % от среднего) и краткие выводы.

**03. Анализ района** (`/districts`)
- Руководитель заполняет данные: конкуренты, уровень цен, жилая застройка, новые стройки,
  инфраструктура, спрос, перспективы, аренда, логистика.
- Взвешенная оценка 0–100 по восьми критериям, лепестковая диаграмма, вердикт и рекомендация.
- Оценка пересчитывается прямо во время заполнения формы.

**04. Бонусная система и интеграция с 1С**
- 1 % от суммы завершённого заказа начисляется автоматически (триггер БД), ручные операции — на `/bonuses`.
- HTTP-методы обмена с 1С: клиенты, заказы, бонусы (GET — выгрузка, POST — загрузка).
- Журнал обмена, настройки и переключатели синхронизации на `/integration`.

**05. Финансы** (`/finance`, только руководитель/администратор) — заменяет прежнюю страницу
«Отчётность»; помесячная и годовая динамика продаж теперь показывается прямо на дашборде.
- «Отчёт за месяц» — помесячная выгрузка «Анализ счёта 51» из 1С (`.xls`/`.xlsx`), движение денег
  по расчётному счёту с разбивкой по статьям. Разбор ищет таблицу по заголовку «Кор. Счет», а не по
  фиксированной раскладке колонок — выгрузки 1С за разные месяцы могут отличаться составом колонок.
- Статьи движения денег на графиках укрупнённые (поставщики, покупатели, кредиты, зарплата,
  налоги и т.д.) — статья определяется по номеру корр. счёта, а не по вольному тексту комментария
  из 1С, иначе одна и та же операция из-за опечаток бухгалтера превращалась бы в несколько строк.
- Годовая бухгалтерская отчётность (баланс + отчёт о финансовых результатах, формы
  0710001/0710002) в PDF — коды строк и значения разбираются из текста файла; если код в
  конкретном году не найден, строка просто не появляется, значения других строк не страдают.
- Годовые своды по счёту 51 («... за 2024 г.») система отклоняет — нужен файл за конкретный месяц,
  иначе данные задвоятся в помесячной статистике.
- Если сумма строк не сходится со строкой «Оборот» в самом файле 1С — раздел показывает
  предупреждение, а не скрывает расхождение.
- Сводка (чистый денежный поток, выручка и прибыль за год) выводится на общий дашборд.

## Установка

### 1. Зависимости

```bash
npm install
```

### 2. Проект Supabase

Создайте проект на [supabase.com](https://supabase.com), затем примените по очереди:

1. все файлы из `supabase/migrations/` по порядку номеров (0001 → … → 0006) — таблицы, триггеры,
   RLS, бакет Storage;
2. `supabase/seed.sql` — демо-данные (магазины, номенклатура, клиенты, заказы за 8 месяцев).

Применить можно вручную через SQL Editor (вставить содержимое файла и Run), либо скриптом —
`npx tsx scripts/apply-migration.ts supabase/migrations/000N_name.sql`, если в `.env.local` задан
`DATABASE_URL` (см. `.env.example` — берётся из Project Settings → Database → Connection pooling →
Session pooler; обычная connection string на порт 5432 часто недоступна по сети, у Supabase она
теперь на IPv6).

### 3. Переменные окружения

Скопируйте `.env.example` в `.env.local` и заполните:

```
NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
SUPABASE_SERVICE_ROLE_KEY=<service role key>
INTEGRATION_1C_API_KEY=<произвольный секрет для обмена с 1С>
NEXT_PUBLIC_APP_URL=http://localhost:3000
```

`SUPABASE_SERVICE_ROLE_KEY` нужен для создания сотрудников из CRM и для методов обмена с 1С.

### 4. Первый пользователь

В Supabase → Authentication → Users создайте пользователя с паролем. Профиль создастся
автоматически с ролью `manager`; чтобы выдать права руководителя, выполните в SQL Editor:

```sql
update public.profiles set role = 'director' where email = 'you@stroymat.ru';
```

Дальше сотрудников можно заводить прямо в CRM на странице «Пользователи».

### 5. Запуск

```bash
npm run dev
```

## Обмен с 1С

Все запросы требуют заголовок `x-api-key: <INTEGRATION_1C_API_KEY>`.
Обмен должен быть включён в настройках CRM (`/integration`), иначе методы отвечают `409`.

| Метод | Назначение |
| --- | --- |
| `GET /api/1c/clients?since=<ISO>` | Выгрузка клиентов из CRM |
| `POST /api/1c/clients` | Загрузка клиентов из 1С (upsert по `external_1c_id`) |
| `GET /api/1c/orders?since=<ISO>` | Выгрузка заказов с составом |
| `POST /api/1c/orders` | Загрузка заказов, суммы пересчитываются в CRM |
| `GET /api/1c/bonuses?client=<external_id>` | Бонусные балансы |
| `POST /api/1c/bonuses` | Начисления и списания баллов из 1С |

Пример:

```bash
curl -X POST https://<app>/api/1c/clients \
  -H "x-api-key: $INTEGRATION_1C_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"clients":[{"external_1c_id":"К-000045","name":"ООО «СтройДом»","inn":"7701234567"}]}'
```

Служебная проверка доступности: `GET /api/health`.

## Формат загружаемых отчётов

Парсер сам находит строку заголовков и сопоставляет колонки по синонимам:

| Поле | Распознаваемые заголовки |
| --- | --- |
| Дата | дата, дата документа, дата заказа, период, date |
| Клиент | клиент, контрагент, покупатель, заказчик |
| Документ | номер, заказ, документ, № |
| Номенклатура | номенклатура, товар, наименование, материал |
| Количество | количество, кол-во, объём, qty |
| Сумма | сумма, выручка, итого, стоимость, amount |

Строки без суммы, клиента и номенклатуры считаются служебными и пропускаются.

## Деплой на Vercel

1. Запушьте репозиторий на GitHub.
2. В Vercel импортируйте проект, добавьте те же переменные окружения.
3. Деплой — сборка проходит командой `next build` без дополнительных настроек.
